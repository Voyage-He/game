# Feature Specification: 精简界面无意义UI、减少纵向内容展

**Feature Branch**: `008-reduce-ui-clutter`

**Created**: 2026-05-24

**Status**: Draft

**Input**: User description: "减少界面无意义的UI，减少纵向内容展：1. 比如房间号没必要显示 2.【当前阶段】展示内容占据过大 3. 玩家身份牌应该横向排列 4. 卡牌大小应该更小，尤其是移动端"

## Constitution Alignment *(mandatory)*

- **服务端权威与规则一致性**: ✅ PASS — UI 变更仅涉及客户端 HTML/CSS 渲染，不修改服务端游戏逻辑、阶段计时、身份规则或 Socket.IO 协议。服务端权威性不变，所有游戏规则和阶段推进行为与变更前完全一致。
- **临时数据与隐私最小化**: ✅ PASS — 本次变更不引入新数据存储或传输。所有 UI 展示数据（房间码、阶段名称、玩家昵称、卡牌身份）均来自已有的 `PublicRoomView` / `PrivateRoomView` 字段，不增加任何数据收集点。
- **测试先行与契约可验证**: ✅ PASS — 需验证：房间号不再可见，阶段标识尺寸减小，玩家卡牌横向排列，卡牌实际尺寸在桌面端和移动端均缩小。E2E 截图对比可验证布局变更。
- **简洁自托管架构**: ✅ PASS — 零新依赖。纯 CSS 修改 + 少量 HTML 结构微调。不引入图标库、UI 框架或图片资源。
- **清晰中文体验与实时可用性**: ✅ PASS — 移除无意义信息（房间号）减少视觉噪音；缩小阶段标识释放纵向空间；横向排列减少页面滚动；更小的卡牌让移动端一屏内可见更多信息。所有变更提升信息密度和阅读效率。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 移除无意义的房间号展示 (Priority: P1) 🎯 MVP

作为玩家，在进入游戏房间后，我不需要看到占据标题位置的房间号（因为我已通过链接或输入进入，无需反复确认房间号）。移除房间号后页面顶部更清爽，减少了一条无意义的纵向信息。

**Why this priority**: 房间号是纯技术标识，对游戏体验无任何价值。这是最简单、最明确的精简变更。

**Independent Test**: 进入游戏房间，验证页面顶部不再显示"房间 XXXXXX"标题，页面直接展示游戏核心信息。

**Acceptance Scenarios**:

1. **Given** 玩家处于游戏房间中，**When** 查看页面顶部，**Then** 不再看到"房间 XXXXXX"文字。
2. **Given** 玩家处于大厅界面（未加入房间），**When** 查看页面，**Then** 大厅房间码展示（用于复制邀请）保持不变或改为更紧凑的内联样式。

---

### User Story 2 - 缩小当前阶段标识尺寸 (Priority: P1)

作为玩家，我需要在游戏中快速获知当前阶段，但不需要一个占据大量纵向空间的超大标题。当前阶段标识应改为紧凑的内联展示（如小标题 + 图标/徽章），减少从阶段标识到操作区域之间的视觉距离。

**Why this priority**: 当前 `<h2>` 阶段标题字体达到 `clamp(1.6rem, 5vw, 2.5rem)`，在移动端约占半屏高度，与计时器和操作区域之间产生不必要的纵向空白。缩小后信息更紧凑。

**Independent Test**: 对比变更前后游戏界面的首屏信息量，验证阶段标识垂直占用空间减少至少 40%。

**Acceptance Scenarios**:

1. **Given** 玩家处于任意游戏阶段，**When** 查看阶段标识，**Then** 阶段名称以紧凑样式展示（如小标题 + 内联徽章），不再独占大面积卡片区域。
2. **Given** 移动端视口（宽度 ≤ 640px），**When** 查看阶段标识，**Then** 阶段名称、倒计时、行动提示在首屏内无需滚动即可完整可见。

---

### User Story 3 - 玩家身份牌横向排列 (Priority: P2)

作为玩家，我希望看到三名玩家的身份牌水平并排展示，而非当前昵称在上、卡牌在下的纵向堆叠。横向排列更符合"扑克牌桌面"的直觉，三张牌一目了然，减少纵向滚动。

**Why this priority**: 当前 `.player-card` 采用 `flex-direction: column`（昵称在上、卡牌在下），三人并排时纵向高度为卡牌高度 + 昵称行高。改为横向排列（昵称在卡牌侧边或上方）后可以容纳更紧凑的布局。

**Independent Test**: 检查 `.players-grid` 中每个 `.player-card` 的内部布局，验证昵称和卡牌处于水平并排或紧凑的行内关系，而非上下堆叠。

**Acceptance Scenarios**:

1. **Given** 三名玩家在游戏中，**When** 查看玩家卡牌区域，**Then** 每名玩家的身份牌与昵称/徽章处于水平排列（如昵称在卡牌下方、上方或侧面，整体横向布局）。
2. **Given** 移动端视口，**When** 三名玩家并排展示，**Then** 不会因为纵向堆叠导致需要滚动才能看到全部三张卡牌。

---

### User Story 4 - 卡牌尺寸缩小（桌面端和移动端） (Priority: P1)

作为玩家，尤其是在移动端屏幕较小的设备上，当前的卡牌尺寸（140×210px 桌面端，移动端弹性缩放至 100×150px）仍然偏大，导致三张水下牌 + 三张玩家牌需要大量滚动才能看完。缩小卡牌尺寸可以让所有关键信息在一屏内可见。

**Why this priority**: 卡牌是界面中占面积最大的元素。缩小卡牌直接、显著地减少纵向内容展。移动端尤其关键——当前卡牌尺寸导致需要频繁滚动。

**Independent Test**: 测量 `.card` 元素渲染尺寸，桌面端目标约 100×150px（较当前减少约 30%），移动端目标约 80×120px（较当前减少约 20%）。

**Acceptance Scenarios**:

1. **Given** 桌面端视口（宽度 > 640px），**When** 查看卡牌元素，**Then** 卡牌宽度约为 100px（较当前 140px 减少约 30%），高度等比缩小至约 150px。
2. **Given** 移动端视口（宽度 ≤ 640px），**When** 查看卡牌元素，**Then** 卡牌宽度在 80–96px 范围内（较当前 100–140px 缩小），三张水下牌 + 三张玩家牌在首屏内无需滚动即可全部可见。
3. **Given** 卡牌尺寸缩小后，**When** 卡牌翻转动画播放或点击交互触发，**Then** `card-flip-in` 动画、`:hover` 缩放、`:active` 按下效果均正常适配新尺寸（无裁切、偏移或动画异常）。

---

### Edge Cases

- **卡牌缩小后的文字可读性**：`.card-role` 身份文字（当前 `font-size: 1.4rem`）随卡牌缩小需等比缩小，确保中文身份名称（如"捣蛋鬼"三字）在小卡牌上不溢出、可清晰辨认。
- **点击交互区域**：缩小后卡牌可点击区域相应减小，触摸设备上需确保可点击面积 ≥ 44×44px（WCAG 触摸目标最小尺寸建议），必要时通过 padding 扩大点击热区而不增大视觉尺寸。
- **水下牌特殊背景**：水下牌的渐变色背景（`linear-gradient(135deg, #0d7377...)`）和纹理装饰（`repeating-linear-gradient`）在缩小后应保持视觉辨识度，不因缩小而失去与玩家牌（蓝色背面）的区分。
- **卡牌翻转动画**：CSS 3D `rotateY(180deg)` 翻转动画在缩小后的卡牌上继续正常工作，`perspective: 800px` 可能需要调整以获得最佳 3D 效果。
- **结算阶段卡牌展示**：结算阶段展示的最终身份牌（`card-flip-in` 入场动画）尺寸应与常规卡牌一致，不因结算展示而使用不同尺寸。
- **长昵称截断**：横向排列后昵称可用宽度可能减少，需确保长昵称（最多 20 字符）以省略号截断或换行，不破坏横向布局。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 从游戏房间界面移除房间号（`roomCode`）展示。大厅界面的房间码展示（供复制邀请）可保留但宜改为紧凑样式。
- **FR-002**: 系统 MUST 将阶段标识（当前 `.phase-card` 中的 `<span class="badge">当前阶段</span>` + `<h2>`）改为紧凑展示，垂直占用空间减少 ≥ 40%。阶段名称文字信息不丢失。
- **FR-003**: 系统 MUST 将玩家身份牌布局从纵向堆叠（昵称在上、卡牌在下）改为水平排列：昵称和徽章置于卡牌下方或侧方，`.player-card` 内部改为行内或紧凑的行向布局。
- **FR-004**: 系统 MUST 将桌面端卡牌默认尺寸从 140×210px 缩小至约 100×150px（宽度减少约 30%，高度等比减少）。
- **FR-005**: 系统 MUST 将移动端（≤ 640px 视口）卡牌尺寸缩小至 80–96px 宽度范围（较当前 100–140px 缩小），确保三张水下牌 + 三张玩家牌在首屏内无需滚动可见。
- **FR-006**: 系统 MUST 在卡牌缩小后保持 `.card-role` 身份文字的清晰可读性和不溢出。
- **FR-007**: 系统 MUST 在卡牌缩小后保持点击交互可用性（触摸目标 ≥ 44×44px）。
- **FR-008**: 系统 MUST 保持水下牌与玩家牌的视觉区分（不同背面颜色/纹理）在缩小后依然可辨识。
- **FR-009**: 系统 MUST 保持卡牌翻转动画（`card-flip-in`）、悬停效果（`:hover`）、按下效果（`:active`）和选中状态（`.selected`）在新尺寸下正常工作。
- **FR-010**: 系统 MUST 确保长昵称（最多 20 字符）在横向布局中合理截断或折行，不破坏布局。

### Key Entities

- **游戏房间界面 (Game View)**: 客户端渲染的游戏主界面，包含阶段标识、倒计时、水下牌区域、玩家牌区域、行动面板和投票/结算面板。本次重构影响前四个区域的布局和尺寸，行动/投票/结算面板的功能逻辑不变。
- **卡牌元素 (Card Element)**: 桌面端和移动端渲染的`.card` HTML 元素，包含 `.card-inner`（正面/背面翻转容器）。本次变更调整其 CSS 尺寸、内文字号和背面装饰，不改变其 DOM 结构或 JavaScript 交互逻辑。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 游戏房间界面中不再显示房间号文字，页面顶部纵向空间释放。
- **SC-002**: 阶段标识（当前阶段名称 + 徽章）垂直占用空间较变更前减少 ≥ 40%（以 CSS 盒模型高度或截图像素测量）。
- **SC-003**: 三名玩家的身份牌在 `.players-grid` 中以水平排列方式呈现（昵称/徽章在卡牌下方或侧方），每张 `.player-card` 的 flex-direction 为 row 或昵称在卡牌底部。
- **SC-004**: 桌面端卡牌渲染尺寸为宽度约 100px、高度约 150px（±10px 容差），较变更前 140×210px 显著缩小。
- **SC-005**: 移动端（375px 视口宽度）水下牌区域（3 张）+ 玩家牌区域（3 张）+ 阶段标识 + 倒计时在首屏内无需纵向滚动即可全部可见。
- **SC-006**: 中文身份名称（4 个角色：狼人、预言家、强盗、捣蛋鬼，最长 3 字）在缩小后的卡牌正面清晰可读，无溢出或裁切。
- **SC-007**: 所有现有卡牌交互功能（点击翻转揭示、点击选择目标、`:hover`/`:active` 反馈）在新尺寸下正常工作，无回归缺陷。所有 83 个现有测试继续通过。

## Assumptions

- 卡牌尺寸缩小到 100×150px（桌面端）和 80–96px（移动端）是基于当前 140×210px 等比缩小的合理目标，若实际视觉测试后发现文字可读性问题，可在该范围内微调。
- "玩家身份牌横向排列"指每张 `.player-card` 内部昵称与卡牌的水平关系调整，而非三张卡牌之间的排列（三张卡牌之间已通过 `.players-grid: grid-template-columns: repeat(3, 1fr)` 实现并排）。
- 水下牌和玩家牌的缩小比例保持一致，不会出现两种卡牌大小不一的情况。
- 卡牌翻转动画和交互逻辑通过 CSS 过渡实现，尺寸变更不影响动画时序（`0.5s ease`），仅需确保 `perspective` 值适配新尺寸。
- 聊天面板、投票面板、行动提示面板的内容和尺寸保持不变，本次变更仅聚焦阶段标识区域和卡牌区域。
- 大厅界面（房间创建/加入表单）的布局不在本次变更范围内，仅游戏房间界面的房间号移除属于本次范围。
